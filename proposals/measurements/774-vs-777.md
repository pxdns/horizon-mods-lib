## What a translator adds per packet (a microbenchmark of its own operations)

Run with `cd tools/measure/bench && cargo run --release`. It uses std only and synthetic data, on the build machine of this
session (a shared cloud container, one run, so read the numbers as orders of magnitude). It measures what a translator adds,
**not** how fast Horizon's own decode is.

| Operation | Cost |
|---|---|
| id lookup and forward unchanged (`Frame::Same`) | about 2 ns per packet |
| indirect chunk section: remap a 64-entry palette | about 20 ns per section |
| direct chunk section: remap 4096 packed 15-bit entries | about 8 µs per section |
| direct chunk, all 24 sections direct (the worst case) | about 0.2 ms per chunk |
| window contents: remap 46 stacks | about 30 ns per packet |

Reading it: the pass-through path is a table lookup, so a translator costs nothing measurable on the packets that do not change.
Chunks are the only packets where translation work is visible; most sections use an indirect palette, where only the palette is
rewritten. Even a chunk of nothing but direct sections costs about 0.2 ms, so joining with a view distance of 10 (about 440 chunks)
is under 0.1 s of work spread over the join, on the network thread and not the game thread. That supports "no lag difference" for
the id remapping; it does not cover decompression, light data, block entities or biome containers, which a real translator also
touches.

## What this says

- **Horizon's ids are right.** `ids.rs` equals Mojang's 26.3 report for every state and direction, so the 777 side of the table is
  known exactly.
- **Most of the work is id tables, and the tables can be generated.** Of 250 play and configuration packets shared by 1.21.11 and
  26.3, 176 (70 %) have a different id, almost all in the play state. The same holds for registries: 1479 of 1505 item ids, 1143 of 1166
  block ids and 124 of 157 entity type ids move, because new entries are inserted in the middle. These are lookup tables built from
  the reports, not logic, and they are the same files the generator already writes for each version.
- **The three steps are very unequal.** 774 -> 775 adds one item, two blocks and five play packets, and changes the layout of ten
  packets. 775 -> 776 moves no packet id at all (one serverbound packet replaced by another) and adds 31 items, 28 blocks and one
  entity type. 776 -> 777 is the big one: 131 packets change id, 121 items, 90 blocks and 3 entity types are added, and 4 play
  packets are new for the client to send.
- **The client is the newer side, which makes the direction easier.** A 1.21.11 server only sends ids that exist in 1.21.11, so
  clientbound translation is remapping old ids to new ones, with nothing to invent: no 1.21.11 item or block is missing from 26.3
  (nothing is "only before" in the registry tables). The packets that need real logic are the ones Horizon *sends* that 1.21.11 has
  no name for: `attack`, `punch`, `set_game_rule` and `spectator_action` (and `swing` is renamed to `swing_animation` the other way).
  Those must be turned into what a 1.21.11 server expects (an attack as an entity interaction plus an arm swing, and so on) or
  dropped.
- **What is still not measured.** Field layouts for 775, 776 and 777: the Mojang reports hold ids only, minecraft-data has 774 and
  775 (ten packets differ), and Horizon's decoders are the only source for the last two steps. Chunk, light and component formats are
  the likely cost; this table says nothing about them.
