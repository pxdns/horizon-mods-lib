## What a translator adds per packet (a microbenchmark of its own operations)

Run with `cd tools/measure/bench && cargo run --release`. It uses std only and synthetic data, on the build machine of this
session (a shared cloud container, one run, so read the numbers as orders of magnitude). It measures what a translator adds,
**not** how fast Horizon's own decode is.

| Operation | Cost |
|---|---|
| id lookup and forward unchanged (`Frame::Same`) | about 2 ns per packet |
| indirect chunk section: remap a 64-entry palette | about 20 ns per section |
| direct chunk section: remap 4096 packed 15-bit entries | about 8 µs per section |
| direct chunk, all 24 sections direct (the worst case) | about 0.2 ms per chunk |
| window contents: remap 46 stacks | about 30 ns per packet |

Reading it: the pass-through path is a table lookup, so a translator costs nothing measurable on the packets that do not change,
which is most of them. Chunks are the only packets where translation work is visible. Most sections use an indirect palette, where
only the palette is rewritten, which is cheap. Even a chunk of nothing but direct sections costs about 0.2 ms, so the worst case
for joining with a view distance of 10 (about 440 chunks) is under 0.1 s of work spread over the join, on the network thread and
not the game thread. That supports the claim that "no lag difference" is reachable for the id remapping; it does not cover
decompression, light data, block entities or biome containers, which a real translator also touches.

## What this says

- **The 774 -> 775 step is small.** No packet was added or removed in the handshake, status, login or configuration states, and
  only 5 play packets were added. 10 of 252 shared packets changed layout (`update_time`, `advancements`, `use_entity`, `block_place`,
  `use_item`, `client_command`, `chat_command_signed`, `enchant_item`, `arm_animation`, `open_book`). One new item and two new blocks
  (`golden_dandelion`, `potted_golden_dandelion`) are the only registry entries added; it is a one-item insertion that shifts most
  numeric ids (1275 of 1505 item ids, 1008 of 1166 block ids, states of 1056 blocks), which is table work, not logic.
- **774 -> 777 is at least 10 packets of net change** by count (play clientbound +5, serverbound +3, one more configuration packet,
  one fewer handshake packet), plus layout changes that were not measured for 776 and 777.
- **Not known yet:** which packets changed id between 774 and 777, how many layouts changed in 775 -> 777, and the id tables of
  26.2 and 26.3. All three need Mojang's data generator reports (or Horizon's decoders) and were not produced here.
